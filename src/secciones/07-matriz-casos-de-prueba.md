# Matriz de casos de prueba

## Objetivo de la estrategia de pruebas

La estrategia de pruebas tiene como objetivo verificar que el sistema de gestión de biblioteca cumpla los requerimientos funcionales y las reglas de negocio definidas para sus procesos críticos. La matriz cubre los flujos principales del sistema, sus validaciones, los escenarios de error y los controles de autenticación y autorización.

Las pruebas se diseñaron siguiendo la siguiente trazabilidad:

Requerimiento → criterio de aceptación → caso de prueba → resultado esperado → evidencia.

Se consideran casos de camino exitoso, casos negativos, validaciones de datos, restricciones de negocio y permisos de seguridad. Los resultados obtenidos de la ejecución de estos casos se presentan en el punto 8 del informe.

## Tipos de prueba considerados

| Tipo de prueba              | Propósito                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------ |
| Camino exitoso o happy path | Comprobar que una operación válida se complete correctamente.                        |
| Caso negativo               | Confirmar que el sistema rechace una operación inválida o no permitida.              |
| Validación de datos         | Verificar formatos, dominios, obligatoriedad y reglas de entrada.                    |
| Regla de negocio            | Comprobar restricciones como disponibilidad, plazos, sanciones y estados.            |
| Autenticación               | Verificar el acceso mediante contraseña y segundo factor MFA.                        |
| Autorización                | Confirmar que cada rol solo pueda ejecutar las operaciones que le corresponden.      |
| Integridad y trazabilidad   | Verificar que los cambios de estado y la bitácora conserven información consistente. |
| Integración                 | Comprobar la comunicación entre frontend, API, base de datos y servicio de correo.   |

## Condiciones generales de prueba

Las pruebas se ejecutan sobre la aplicación web compuesta por un frontend React y un backend Django REST Framework. Para los casos funcionales se considera una base de datos con usuarios, estudiantes, categorías, títulos, ejemplares y préstamos de prueba.

### Datos y estados requeridos

- Un usuario administrador activo con MFA configurado.
- Un usuario operador activo con MFA configurado.
- Un usuario operador temporal dentro de su período de vigencia.
- Un usuario temporal cuya fecha de vigencia haya expirado.
- Un estudiante habilitado, sin préstamos vencidos ni sanciones vigentes.
- Un estudiante con un préstamo vencido o una sanción vigente.
- Un ejemplar disponible.
- Un ejemplar actualmente prestado.
- Un ejemplar en mantenimiento o dado de baja.
- Una cuenta de correo de prueba para verificar el comprobante digital.

## Criterios de aprobación

Un caso se considera aprobado cuando el resultado observado coincide con el resultado esperado y existe evidencia verificable, como una captura de pantalla, una respuesta de la API, un registro de base de datos, un correo de prueba o el resultado de una prueba automatizada.

Los casos de prioridad alta corresponden a funciones que afectan directamente la seguridad, la integridad del inventario, la trazabilidad o la continuidad del préstamo. Si alguno de estos casos falla, la versión no debería considerarse lista para una demostración final sin registrar el defecto y su impacto.

La matriz debe ejecutarse en un entorno controlado y con datos de prueba. En el caso de pruebas relacionadas con correo, se deben utilizar cuentas autorizadas para testing y evitar el envío accidental de información a estudiantes reales.

## Cobertura esperada

La matriz cubre los caminos principales de autenticación, administración de usuarios, inventario, catálogo, préstamos, comprobantes, devoluciones, sanciones, auditoría y renovación de sesión. También incluye escenarios negativos y controles de seguridad, cumpliendo con la exigencia de verificar tanto el comportamiento correcto como el rechazo de operaciones inválidas o no autorizadas.

Los resultados de la ejecución, la comparación entre lo esperado y lo obtenido, los hallazgos y las evidencias concretas deben documentarse en el punto 8 del informe.
